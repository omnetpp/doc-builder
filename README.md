# OMNeT++ doc-builder

The toolchain that builds the documentation sites of [OMNeT++](https://omnetpp.org) and of the simulation models
built on it:

| Part | What it is |
|------|------------|
| [`action.yml`](action.yml) | A GitHub Action (this page) that builds the documentation website of a model project for GitHub Pages in the image: the NED reference, optionally a Sphinx site, the C++ API (doxygen) and PDFs |
| [`image/`](image/README.md) | The `ghcr.io/omnetpp/doc-builder` container image: Sphinx, doxygen, `opp_docgen`, TeX Live and the rest of the toolchain, with the extensions below |
| [`extensions/`](extensions) | The OMNeT++ Sphinx extensions in the image: the look of the OMNeT++ sites (`omnetpp_immaterial`), links to the NED reference (`omnetpp_neddoc`) and to the C++ API (`omnetpp_doxylink`), NED/MSG/ini highlighting (`omnetpp_lexers`), video and audio (`omnetpp_media`); described in the image's README |

The action builds the documentation website of an OMNeT++ model project, ready for GitHub Pages, in the OMNeT++
doc-builder image (`ghcr.io/omnetpp/doc-builder`, the toolchain of [docs.omnetpp.org](https://docs.omnetpp.org)
and [inet.omnetpp.org](https://inet.omnetpp.org)):

- the **NED reference** of the project's NED and MSG files, generated by `opp_docgen`;
- optionally a **Sphinx site** (your hand-written documentation) that the NED reference becomes part of;
- optionally the **C++ API**, generated by doxygen, linked from the NED types' pages;
- optionally **PDFs** of the Sphinx site.

The action builds the site into a directory and, by default, uploads it as the GitHub Pages artifact. The
deployment is a second job of your workflow (see below), because it needs permissions that the build does not.

## Quick start: the NED reference

`.github/workflows/docs.yml` in your model repository:

```yaml
name: Documentation

on:
  push:
    branches: [master]
  workflow_dispatch:

concurrency:
  group: pages
  cancel-in-progress: false

jobs:
  build:
    runs-on: ubuntu-latest
    permissions:
      contents: read
    steps:
      - uses: actions/checkout@v7
      - uses: omnetpp/doc-builder@v1

  deploy:
    needs: build
    runs-on: ubuntu-latest
    permissions:
      pages: write
      id-token: write
    environment:
      name: github-pages
      url: ${{ steps.deployment.outputs.page_url }}
    steps:
      - id: deployment
        uses: actions/deploy-pages@v5
```

and once, in the repository settings: **Settings → Pages → Build and deployment → Source: GitHub Actions**.

This publishes the NED reference of the project in the repository root, in the look of the Eclipse-based IDE's
NED documentation (`ned-format: html-material`; `html-readthedocs` and `html` are the other choices). The NED
folders of the project are taken from its `.nedfolders` file, like in the IDE.

Add `doxygen: true` to also publish the C++ API, under `api/`. The NED types' pages then link to their C++
classes ("C++ definition").

## A Sphinx site

With `sphinx-source`, the site is built from your Sphinx project, and the NED reference (and the C++ API)
become pages of it:

```yaml
      - uses: omnetpp/doc-builder@v1
        with:
          sphinx-source: doc
          doxygen: true
```

The action generates the NED reference as reStructuredText into `<sphinx-source>/ned` (`ned-dir`) and the C++
API into `<sphinx-source>/api` (`api-dir`), then runs `sphinx-build` in the Sphinx project. Your project
refers to them from a toctree:

```rst
.. toctree::

   guide
   NED Reference <ned/index>
   C++ API <api/index>
```

and ignores them in git, since they are generated (`doc/.gitignore`):

```
/ned/
/api/
```

The action does not change `conf.py`; it is yours. The image provides Sphinx, `sphinx_immaterial` and a few
OMNeT++ extensions; a `conf.py` that gives the site the look of the OMNeT++ sites:

```python
project = 'My Model'

extensions = [
    'sphinx_immaterial',
    'omnetpp_immaterial',   # the look of the OMNeT++ sites
    'omnetpp_neddoc',       # the :ned: and :msg: roles, NED/MSG highlighting, linked diagrams
    'omnetpp_doxylink',     # the :cppref: role, linking to the C++ API (with doxygen: true)
    'omnetpp_media',        # video, audio, youtube and vimeo directives (optional)
]
html_theme = 'sphinx_immaterial'

doxylink = {'cppref': ('api/tagfile.xml', 'api/')}
```

`omnetpp_neddoc` finds the NED reference in `ned` (its `neddoc_dir` setting; change it together with `ned-dir`).

The NED reference and the C++ API have a page per type, too many for the navigation that Sphinx puts into every
page. `omnetpp_immaterial` shows them in the sidebar as trees that the browser loads when the reader opens them:
the NED reference by packages, kinds of types and files, the C++ API by namespaces and classes. It
needs no setting: it finds the NED reference through `omnetpp_neddoc`, and the C++ API by the `tagfile.xml` next to
`api/index`. The trees appear under the entries of `ned/index` and `api/index` in your toctree.

[`test/sample-model/doc`](test/sample-model/doc) is a complete example. Pages of the site refer to

- NED and MSG types with `omnetpp_neddoc`, by their short or full names: `` :ned:`Source` ``,
  `` :ned:`the source <sample.Source>` ``, `` :msg:`Job` ``;
- C++ classes with doxylink: `` :cppref:`sample::Source` ``.

To build the site locally while writing it, see [Running locally](#running-locally).

## The C++ API

`doxygen: true` runs doxygen with a bundled configuration (that of the OMNeT++ API documentation, with
[doxygen-awesome](https://github.com/jothepro/doxygen-awesome-css)) on the header files under
`<project-dir>/src` (`doxygen-input`; generated `*_m.h` files are excluded). Undocumented members are left out.

`doxyfile` replaces the bundled configuration with yours. Either way, the action overrides the output settings
(`OUTPUT_DIRECTORY`, `HTML_OUTPUT`, `GENERATE_TAGFILE`, ...), and, in a Sphinx site, those that the wrapping of
the pages into the site needs (`GENERATE_TREEVIEW = NO`, `DISABLE_INDEX = NO`, `SEARCHENGINE = NO`). Paths in
the doxyfile are relative to the working directory, i.e. the repository root.

In a Sphinx site, the doxygen pages are wrapped into Sphinx pages by `doxysphinx`, like in the OMNeT++
documentation, without doxygen's own title and navigation bar, and `api/index` is the class list. Only the
overview pages (class hierarchy, class index, namespace list) and the topic pages are in the site navigation,
under `api/index`; the class, namespace and file pages are not, so that a large API does not add an entry per
class to the navigation of every page. The sidebar's tree of the C++ API (see [A Sphinx site](#a-sphinx-site))
lists them instead. Doxygen comments can contain reStructuredText between `\rst` and `\endrst`.

## PDF

With `pdf: true`, the action also builds the Sphinx project with `sphinx-build -M latexpdf` (the image has
TeX Live), and copies the PDFs into the root of the site, where the pages can link to them. What goes into the PDFs is up to `latex_documents` in `conf.py`. The NED reference and the C++ API
are pages for the web, so let the PDF's root document be one that does not include them, e.g. a guide:

```python
latex_documents = [('guide', 'my-model.tex', project, author, 'manual')]
```

doxylink cannot link from a PDF to the C++ API on the site by a relative path, and warns about it: with
`fail-on-warnings`, keep `:cppref:` out of the PDF's documents, or give doxylink the API's absolute URL.

Without `sphinx-source` there is no PDF: `opp_docgen` writes none.

## Models that build on other models

A model that uses the NED types of another one (e.g. INET) needs the other's NED files, to resolve the types it
uses. They are not documented, but linked to, if you tell where their documentation is:

```yaml
      - uses: actions/checkout@v7
      - uses: actions/checkout@v7
        with:
          repository: inet-framework/inet
          ref: v4.6.0
          path: inet
      - uses: omnetpp/doc-builder@v1
        with:
          ned-path: inet/src
          external-docs: inet=https://inet.omnetpp.org/docs/latest/api/types
```

`external-docs` maps NED packages to the documentation of their types; a type's page is
`<url>/<qualified name>.html`, so the URL above links to the NED reference of the latest INET release. The pages
of message types are named differently, which `opp_docgen` can only know from the tag files of the dependency's
documentation (`msgtags.xml`); INET does not publish them, so the links to INET's message types do not work.

In the pages of a Sphinx site, `:ned:` and `:msg:` link only to the project's own types: the name of a
dependency's type renders as code, with a `neddoc.unknown` warning (`suppress_warnings = ['neddoc.unknown']` in
`conf.py` silences it). Link to the dependency's page with an ordinary link instead.

Remember to exclude the checkout from your own documentation if it is under your project directory and you have
no `.nedfolders`, e.g. with `docgen-args: -x inet`.

## Inputs

All paths are relative to the working directory (the repository root), and must be in it.

| Input | Default | Meaning |
|-------|---------|---------|
| `project-dir` | `.` | the OMNeT++ project whose NED and MSG files are documented |
| `output-dir` | `_site` | where the site is built |
| `title` | name of the project dir | title of the NED reference and the C++ API |
| `sphinx-source` | | the Sphinx project (the directory of `conf.py`); without it, the site is the NED reference |
| `ned-dir` | `ned` | where the NED reference is generated in the Sphinx project |
| `ned-format` | `html-material` | format of the NED reference without Sphinx: `html-material`, `html-readthedocs` or `html` |
| `ned-path` | | NED source roots of dependencies, `;`- or `:`-separated, indexed but not documented |
| `external-docs` | | documentation of dependencies, as `<package>=<url>` items (`opp_docgen -l`) |
| `docgen-args` | | further `opp_docgen` arguments, split at whitespace, without quoting (see `opp_docgen --help` in the image) |
| `doxygen` | `false` | also generate the C++ API |
| `doxygen-input` | `<project-dir>/src` | source directories for the bundled doxygen configuration |
| `doxyfile` | | own doxygen configuration instead of the bundled one |
| `api-dir` | `api` | where the C++ API is generated, in the Sphinx project or in the site |
| `pdf` | `false` | also build PDFs of the Sphinx project, into the root of the site |
| `sphinx-args` | | further `sphinx-build` arguments, split at whitespace, without quoting, e.g. `-j auto` |
| `fail-on-warnings` | `false` | fail if `opp_docgen` or Sphinx (also the PDF build) warn |
| `image-tag` | the action's version | tag of `ghcr.io/omnetpp/doc-builder`; `latest` if the action is used at another branch or a commit |
| `image` | | image to use instead, as is (`image-tag` does not change it) |
| `upload-pages-artifact` | `true` | upload the site as the GitHub Pages artifact |

| Output | Meaning |
|--------|---------|
| `site-dir` | absolute path of the built site |

The directories that the action generates (`output-dir`, and `ned-dir` and `api-dir` in the Sphinx project)
are emptied before each build. A directory that is not empty and was not generated by the action (it has no
`.doc-builder` file) is not touched: the build fails instead.

## The image

The image is built from this repository ([`image/`](image/README.md)) and released with the action: by default,
the action runs in the image of its own version, e.g. `omnetpp/doc-builder@v1` in
`ghcr.io/omnetpp/doc-builder:v1`, which is built from the `v1` branch, like the action. To keep the documentation
build stable, use a full version of the action (`omnetpp/doc-builder@v1.2.0`), or pin an image tag with
`image-tag` (see the
[tags](https://github.com/orgs/omnetpp/packages/container/package/doc-builder)). `latest` is the newest image.

The image is `linux/amd64` only, so the action runs on Linux runners (`ubuntu-latest`), with podman or docker.

If you need a build that this action does not do, run your own commands in the image, with the same tools:

```yaml
jobs:
  build:
    runs-on: ubuntu-latest
    container: ghcr.io/omnetpp/doc-builder:latest
    steps:
      - uses: actions/checkout@v7
      - run: opp_docgen --format=rst -o doc/ned . && sphinx-build -b html doc _site
      - uses: actions/upload-pages-artifact@v5
        with:
          path: _site
```

## Running locally

`doc-builder.sh` is the whole action; it runs the same build on your machine, with podman (or docker:
`ENGINE=docker`). From the repository root of your model, with a checkout of this repository next to it:

```bash
../doc-builder/doc-builder.sh --sphinx-source doc --doxygen
```

It takes the inputs as options (`--help` lists them), and builds into `_site`, which you can open in a browser
or serve with `python3 -m http.server -d _site`. Pull the image again (`podman pull
ghcr.io/omnetpp/doc-builder:latest`) to update it. Inside a container that is the image (`ENGINE=none`), it runs
the tools directly.

## Versions

The image and the action share the versions of the repository. A major version is a branch (`v1`), and is what a
workflow normally uses: it gets fixes and new features, but no changes that break existing workflows. Those come
with a new major version. Releases are tags `vMAJOR.MINOR.PATCH` on it; use one, or a commit, to pin an exact
version.

Each version is also an image tag: the image built from the `v1` branch is `:v1`, that of a release `:v1.2.0`, and
the action runs in the image of its own version by default. So after changing the branch, publish its image from
it (`image/build.sh --push`, see [Publishing](image/README.md#publishing)); for a release, tag the commit first.

## Development

- The image is built with [`image/build.sh`](image/build.sh) from the root of this repository; `vscode` there is a
  symlink to a checkout of omnetpp-vscode, whose `opp_docgen` the image bundles (see
  [Build locally](image/README.md#build-locally)).
- The action is `action.yml` at the root of the repository. Its logic is in `doc-builder.sh` beside it, which also
  runs locally, so that it can be tried without pushing it, also with a locally built image (`--image`).
- [`test/`](test) holds a sample model project, which [`.github/workflows/test.yml`](.github/workflows/test.yml)
  builds with the action on every push and weekly.
